## Архитектурная доработка — этап 3: обложки

- Новые сетевые обложки игр и локальные обложки, найденные при сканировании, сохраняются

  Поиск ограничен файлами cover/folder/poster в корне выбранной версии; игровые архивы
  не вскрываются. Формат определяется по сигнатуре, максимальный размер 8 000 000 байт.
- Для доступных старых обложек путь не меняется; отсутствующие обложки можно восстановить
  при следующем сканировании из локального файла. Исходники и старый кэш не удаляются;
  файлы кэша создаются под уникальными именами и не перезаписываются. Автоочистки нет.
  При настройке папки загрузок равной корню игр сама папка covers не импортируется в
  библиотеку, но отдельный интерфейс GameSweep может показывать её при сканировании.
- Проверяется URL каждого редиректа до перехода. Старая DNS-проверка сервера по-прежнему
  не исключает DNS rebinding между проверкой и подключением; полное декодирование картинок
  не выполняется. Ошибки локального кэша и сетевой загрузки логируются; при отсутствии
  обложки показывается заглушка. Новый кэш исключён из Git.

## Архитектурная доработка — этап 4: обнаружение архивов

- При открытии карточки установленной игры создаётся `Incoming_Downloads` в выбранной
  папке загрузок и выполняется первичный поиск; пока карточка видима, он повторяется
  каждые 15 секунд, есть ручное обновление. Кнопка «Обновить» открывает тему игры,
  если она известна. Расположение папки и версии показаны в карточке.
- API принимает только id игры, ищет файлы ZIP/7z/RAR/TAR/TAR.GZ/TGZ в верхнем уровне,
  не следует ссылкам и предлагает лишь точные совпадения нормализованного имени. Осмотр
  содержимого, целостности и завершения скачивания не выполняется; совпадение не является
  подтверждением версии или принадлежности. Ограничения: 5000 записей каталога и 50
  результатов с предупреждением; перечисляются файлы верхнего уровня с этими расширениями.

## Архитектурная доработка — этап 4: предварительная проверка ZIP

- По явному нажатию проверяется центральный каталог выбранного ZIP из обнаруженных для
  этой игры кандидатов. Проверка только читает метаданные, не распаковывает и не пишет
  файлы; другие форматы не поддерживаются на этом шаге. Размер каталога ограничен 4 МиБ,
  количество элементов — 5000, число прочитанных байт и объём памяти ограничены.
- Отвергаются ZIP64, многотомные и самораспаковывающиеся ZIP, повреждённый каталог,
  неизвестное сжатие, шифрование, ссылки/спецфайлы в Unix-атрибутах, подозрительные
  размеры и степени сжатия, опасные имена Windows, коллизии регистров/Unicode и дубли.
  Совпадение версий и принадлежность игре не подтверждаются.
- Идентичность файла проверяется по хэшу атрибутов до, во время и после чтения; это не
  хэш содержимого и не защищает от всех гонок. Не проверяются локальные заголовки,
  полезные данные и CRC, целостность и окончание скачивания, а также все возможные
  типы метаданных ZIP. Прохождение не означает безопасность или готовность к установке;
  отображается соответствующее предупреждение. При изменении файла требуется повторный поиск.
- Локально: 56 Python-тестов, 17 Node-тестов, синтаксис Python и JS, тест на временных
  ZIP и HTTP; synthetic DOM (jsdom) проверяет кнопку и фокус. Windows run 42609719778
  упал на HTTP-тесте; логи недоступны, вероятная причина — разные inode у DirEntry.stat и

## Архитектурная доработка — этап 4: проверка данных ZIP

- Отдельная кнопка по явному нажатию повторно проверяет метаданные, локальные заголовки,
  дескрипторы и CRC stored/deflate потоково, без записи распакованных файлов. Архив и
  остальные файлы не изменяются. Лимиты: 128 МиБ сжатых, 256 МиБ распакованных данных,
  4 МиБ локальных метаданных, одна проверка данных одновременно. Ориентировочный срок
  30 секунд проверяется между операциями, но не прерывает зависшее файловое чтение.
- Это не подтверждение безопасности, подлинности, завершения загрузки или отсутствия
  гонок. Проверка идентичности — по атрибутам, CRC не криптографический хэш. Некоторые
  нестандартные ZIP отвергаются; повторная проверка обязательна перед установкой.
  Установка, распаковка на диск, бэкап и перенос сохранений не реализованы.
- Локально: 60 Python-тестов, 18 Node-тестов, compileall, синтаксис ES-модулей и
  inline JS, HTTP smoke на временных данных и GameSweep 73/73. Проверены оба метода,

## Архитектурная доработка — этап 4: поиск возможных сохранений

- По отдельному нажатию ищутся известные имена файлов и папок только в папке выбранной
  игры внутри текущего корня библиотеки. Пути клиента не принимаются, содержимое файлов
  не читается; найденные папки сохранений не обходятся. Это не бэкап и не манифест:
  AppData, облако и другие имена не проверяются; отсутствие совпадений ничего не доказывает.
- Ограничения: 5000 элементов, 100 подсказок, глубина обхода каталогов 8 (их элементы
  могут быть на уровне 9), один поиск одновременно,
  ориентировочно 10 секунд между операциями; зависший сетевой ввод не прерывается.
  Ссылки и reparse points пропускаются, ошибки и усечение отмечаются как неполный поиск.

## Архитектурная доработка — этап 4: сравнение путей сохранений с ZIP

- Отдельная кнопка для выбранного ZIP повторно проверяет его каталог и запускает поиск
  возможных сохранений внутри текущей папки игры, затем сравнивает относительные пути.
  Показываются совпадения файлов, общие папки и конфликты типов/родительского файла;
  архив и файлы игры не изменяются. Сервер не принимает произвольные пути клиента.
- Сравнение регистронезависимое с нормализацией Unicode и приблизительное: корень игры
  сопоставляется с корнем ZIP, обёртки не выбираются. Папки сохранений не обходятся,
  AppData и облако не проверяются, поэтому отсутствие совпадений не исключает конфликтов.
  Данные ZIP и CRC в этом режиме не проверяются; неполный поиск отмечается. Атрибуты
  архива повторно сверяются после поиска, но это не защита от всех гонок и результат не
  является бэкапом или планом установки. Наследуются ограничения предыдущих этапов.
- Локально: 70 Python и 20 Node тестов, compileall, синтаксис JS, HTTP smoke и GameSweep

## Архитектурная доработка — этап 4: просмотр состава сохранений

- По отдельному нажатию повторно ищутся возможные расположения сохранений; затем показываются
  имена и размеры отдельных найденных файлов и файлов внутри найденных папок. Читаются
  только файловые метаданные; пути клиента не принимаются, файлы не копируются и не меняются.
- Дополнительные лимиты: 5000 элементов, 200 файлов, глубина обхода 8 от каждой найденной
  папки, 1024 байта на относительный путь, один обзор одновременно, ориентировочно 10
  секунд между операциями. Лимиты первичного поиска действуют отдельно. Размеры и сумма
  приблизительны, учитывают все пути, включая жёсткие ссылки; файлы могут быть лишними.
- Пропуски, изменение атрибутов и лимиты отмечаются как неполный обзор. Ссылки и reparse
  points не обходятся намеренно, но гонки и блокирующее чтение полностью не исключены.
  AppData и облако не ищутся; список может устареть и не является безопасным манифестом,

## Архитектурная доработка — этап 4: основа защищённого чтения

- Добавлен изолированный экспериментальный Windows NTFS-примитив чтения, не подключённый
  к API и интерфейсу. Он открывает каждый компонент с OPEN_REPARSE_POINT и удерживает
  дескрипторы каталогов без разрешения удаления/переименования, файл — без разрешения
  записи/удаления; отклоняет reparse points, спецфайлы и жёсткие ссылки. Допустим только
  локальный фиксированный NTFS, чтение блоками до 1 МиБ. На других системах — отказ.
- Это не готовое безопасное копирование: абсолютные открытия не используют handle-relative
  traversal; переназначение диска, существующие отображения памяти, изменение состава
  папок и блокирующий ввод остаются нерешёнными. Примитив не создаёт копий; его нельзя
  использовать как утверждённый манифест или бэкап до отдельных проверок и интеграции.
- Локально: 82 Python-теста (4 Windows-теста пропущены на Linux), 21 Node-тест,
  compileall, синтаксис JS, HTTP smoke и GameSweep 73/73. Windows run 42742125719 прошёл
  тесты, сборку EXE, smoke и артефакт для 736eec2. Логи отдельных тестов недоступны,
  поэтому возможные пропуски junction/hardlink не подтверждены; ручной Windows не проверялся.

## Архитектурная доработка — этап 4: относительные Windows-дескрипторы

- Прототип чтения после первичного открытия корня диска теперь открывает каждый вложенный
  компонент относительно дескриптора родителя через `NtCreateFile`, удерживая цепочку и
  отклоняя reparse points и жёсткие ссылки. Это эксперимент, не подключённый к API/бэкапу.
- Тип тома проверяется по букве до открытия корня: переназначение буквы в этом промежутке
  и привязка открытых объектов к выбранной игре ещё не решены. Существующие отображения
  памяти, изменения состава каталогов, блокирующие вызовы и особенности драйверов также
  требуют работы. Низкоуровневый NT API требует проверки совместимости. Резервное копирование
  и восстановление остаются не реализованы; пользовательские файлы не записываются.
- Локально: 85 Python-тестов (6 Windows-тестов пропущены на Linux), 21 Node-тест,
  compileall, синтаксис JS, HTTP smoke и GameSweep 73/73. Windows run 42743272946 прошёл
  тесты, EXE, smoke и артефакт для 8b8912f; логи отдельных тестов недоступны, возможные
  пропуски junction/hardlink не подтверждены. Ручной Windows и браузер не проверялись.

## Решения и ограничения

- Интерфейс — локальная веб-страница, а не нативное окно. Host/Origin проверки сохранены.
- Целевая архитектура и лимит 200 строк ещё не достигнуты: два больших файла `legacy/`,
  `ui/index.html` и два background.js — зафиксированные исключения. Legacy по-прежнему
  смешивает HTTP, логику и данные; единый формат ошибок не применяется ко всем старым маршрутам.
  Не обещаем, что функции вне проверенных сценариев не сломаны.
- Зависимости намеренно не зафиксированы версиями, как в оригинале; воспроизводимость ограничена.
